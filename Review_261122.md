## 1. Executive Summary

** Code Review am 22.11.2026 mit Gemini Argon:** Das Framework `otp-actor` (v0.3.3) weist sowohl im lokalen Actor-/Supervision-Kern als auch in der gRPC-Remoting-Schicht eine sehr saubere, hochperformante Architektur auf:
- **Strikte Trennung von Control Plane und Data Plane:** 0-Hop-Cache über `tokio::sync::watch` in `ResourceClient::get`, direkter 1-Hop-Pfad in `ActorClient` und typ-gelöschte `ByteEndpoint`-Bridges in `ActorNodeRegistry` ohne Supervisor-Bottleneck im Hot-Path.
- **Zero-Cost Futures im Core:** Native RPITIT (`impl Future`) in `Worker::execute` und `StatefulActor::{handle, handle_cast, on_start, on_stop}` vermeiden `Box::pin`-Allokationen pro lokaler Nachricht.
- **Gehärtetes gRPC-Remoting:** Begrenzte `postcard`-Serialisierung (`BoundedVec` $\le 4\text{ MiB}$), Ablehnung von Trailing-Bytes, Label-Sanitization gegen Log-Injection, Protokoll-Versionierung (`REMOTE_PROTOCOL_VERSION`) und koordinierter 2-Phasen-Shutdown (`HTTP/2 GOAWAY` + Supervisor-Tree-Teardown).
- **Kompilierung & Linter:** `cargo check --all-targets --all-features` und `cargo clippy --all-targets --all-features -- -D warnings` laufen fehler- und warnungsfrei durch.

Insgesamt wurden **22 detaillierte Findings** identifiziert:

### F-01 [Hoch | Korrektheit & Resilience] ✅ Behoben (22.11.2026): `ActorClient::try_cast` führt nach einem Actor-Restart niemals ein Rebinding durch

- **Status:** **Behoben** am 22.11.2026 in [src/actor/stateful_actor.rs](file:///Users/fredi/Data/Projekte/Rust/261102_actor/src/actor/stateful_actor.rs) sowie abgesichert durch 2 neue Integrationstests in [tests/actor_supervision_test.rs](file:///Users/fredi/Data/Projekte/Rust/261102_actor/tests/actor_supervision_test.rs) (`test_try_cast_rebinds_synchronously_after_restart`, `test_try_cast_returns_unavailable_while_restarting_and_supervisor_error_on_terminal_states`).
- **Umsetzung:** `ActorClient::try_cast` prüft im Happy-Path direkt unter `sender.read()` (ohne `Sender`-Clone) und ruft bei `TrySendError::Closed` das nicht-blockierende `try_rebind_sync()` auf. Läuft eine Ersatzinstanz (`SlotState::Running`), wird `self.sender` mit Schutz gegen Stale-Überschreibung aktualisiert und `try_send` sofort wiederholt; bei `Restarting` wird `ActorError::ActorUnavailable` zurückgegeben und bei `Failed` bzw. `Stopped` direkt `ActorError::Supervisor(...)`.

- **Betroffene Stellen:**
  - `src/actor/stateful_actor.rs:1430-1437` (`ActorClient::try_cast`)
  - Praxis-Auswirkung in `examples/microservice_pipeline.rs:230-245` (`IngestionWorker::handle` nutzt ausschließlich `self.sink_client.try_cast(...)`)

#### Problembeschreibung
`ActorClient::try_cast` liest lediglich den aktuell gecachten `Sender` (`self.current_sender()`) und ruft darauf `try_send` auf:

```rust
pub fn try_cast(&self, msg: A::Message) -> Result<(), ActorError<A::Error>> {
    let current_sender = self.current_sender();
    match current_sender.try_send(ActorEnvelope::Cast { msg }) {
        Ok(()) => Ok(()),
        Err(mpsc::error::TrySendError::Full(_)) => Err(ActorError::MailboxFull),
        Err(mpsc::error::TrySendError::Closed(_)) => Err(ActorError::ActorUnavailable),
    }
}
```

Wenn der Ziel-Actor abstürzt und vom Supervisor erfolgreich als Instanz `#2` neu gestartet wird, publiziert der Supervisor sofort `SlotState::Running { instance_id: 2, endpoint: new_tx }` in den `watch`-Kanal (`self.slot_rx`).
Da `try_cast` bei `TrySendError::Closed` jedoch **niemals** in `self.slot_rx` nachsieht (im Gegensatz zu `call` und `cast`, die `rebind_channel` aufrufen), bleibt ein Producer, der ausschließlich `try_cast` zur Lastabwurf-Kommunikation verwendet (wie `IngestionWorker` -> `StorageSink` in `examples/microservice_pipeline.rs`), **für immer** auf der geschlossenen Mailbox von Instanz `#1` hängen und liefert bei jedem weiteren Aufruf `Err(ActorError::ActorUnavailable)`, obwohl Instanz `#2` längst läuft!

#### Behebungsanweisung
Da `watch::Receiver::borrow()` **synchron und blockierungsfrei (0-Hop)** ist, kann `try_cast` im Fehlerfall `TrySendError::Closed(env)` synchron prüfen, ob in `self.slot_rx` bereits ein neuer `SlotState::Running`-Sender vorliegt, den gecachten `self.sender` aktualisieren und `try_send` sofort auf der neuen Instanz wiederholen:

```rust
pub fn try_cast(&self, msg: A::Message) -> Result<(), ActorError<A::Error>> {
    let first_attempt = {
        let guard = self
            .sender
            .read()
            .unwrap_or_else(std::sync::PoisonError::into_inner);
        guard.try_send(ActorEnvelope::Cast { msg })
    };

    match first_attempt {
        Ok(()) => Ok(()),
        Err(mpsc::error::TrySendError::Full(_)) => Err(ActorError::MailboxFull),
        Err(mpsc::error::TrySendError::Closed(env)) => {
            if let Some(new_tx) = self.try_rebind_sync() {
                match new_tx.try_send(env) {
                    Ok(()) => Ok(()),
                    Err(mpsc::error::TrySendError::Full(_)) => Err(ActorError::MailboxFull),
                    Err(mpsc::error::TrySendError::Closed(_)) => Err(ActorError::ActorUnavailable),
                }
            } else {
                Err(ActorError::ActorUnavailable)
            }
        }
    }
}

/// Synchrones, nicht-blockierendes Rebinding über den bereits abonnierten `slot_rx`.
fn try_rebind_sync(&self) -> Option<Sender<ActorEnvelope<A>>> {
    let slot_guard = self
        .slot_rx
        .read()
        .unwrap_or_else(std::sync::PoisonError::into_inner);
    let rx = slot_guard.as_ref()?;
    if let SlotState::Running { endpoint, .. } = &*rx.borrow()
        && let Some(new_tx) = endpoint.downcast_ref::<Sender<ActorEnvelope<A>>>()
        && !new_tx.is_closed()
    {
        let cloned = new_tx.clone();
        drop(slot_guard);
        *self
            .sender
            .write()
            .unwrap_or_else(std::sync::PoisonError::into_inner) = cloned.clone();
        return Some(cloned);
    }
    None
}
```

#### SemVer-Kompatibilität
- **Kein SemVer-Break (Patch-Level Bugfix).**

#### Auswirkung auf `remote`
- **Keine negativen Konsequenzen.** Lokal in `ActorNodeRegistry` registrierte `ActorClient<A>`-Instanzen profitieren direkt davon: Sobald `try_cast` den gecachten `self.sender` aktualisiert, meldet auch `ActorNodeRegistry::snapshot_endpoints()` (`src/remote/registry.rs:152` -> `endpoint.queue_stats()`) sofort die `QueueStats` der neuen Instanz statt `is_closed == true`.

### F-02 [Hoch | Korrektheit & OTP-Semantik] ✅ Behoben (22.11.2026): Parallele statt streng sequenzieller Terminierung in umgekehrter Registrierungsreihenfolge bei `OneForAll`- und `RestForOne`-Restarts

- **Status:** **Behoben** am 22.11.2026 in [src/actor/supervisor.rs](file:///Users/fredi/Data/Projekte/Rust/261102_actor/src/actor/supervisor.rs) (`TerminationPlan`, `remove_child_slot_plan`, `handle_restart_child`, `handle_child_failure`) sowie abgesichert durch 2 neue Integrationstests in [tests/actor_supervision_test.rs](file:///Users/fredi/Data/Projekte/Rust/261102_actor/tests/actor_supervision_test.rs) (`test_one_for_all_crash_and_restart_child_terminate_siblings_sequentially_in_reverse_order`, `test_rest_for_one_crash_and_max_restarts_terminate_downstream_sequentially_in_reverse_order`).
- **Umsetzung:** Alle betroffenen Slots werden weiterhin synchron auf `ChildPhase::Restarting` bzw. `Failed` und `SlotState::Restarting` / `Failed` gesetzt und in `TerminationPlan`s (inkl. entfernter `Temporary`-Geschwister über `remove_child_slot_plan`) überführt. Ein Hintergrund-Task führt anschließend `TerminationPlan::execute_sequence` strikt nacheinander in umgekehrter Registrierungsreihenfolge aus, sodass Kind $k$ erst sein Shutdown-Signal erhält, nachdem Kind $k+1$ vollständig beendet wurde.

- **Betroffene Stellen:**
  - `src/actor/supervisor.rs:1713-1767` (`Supervisor::handle_restart_child`)
  - `src/actor/supervisor.rs:1987-2022` (`Supervisor::handle_child_failure` – Restart-Pfad)
  - `src/actor/supervisor.rs:2090-2137` (`Supervisor::handle_child_failure` – MaxRestartsExceeded-Pfad)

#### Problembeschreibung
Die Dokumentation in `src/lib.rs:15-16` und `src/actor/model.rs:85-92` garantiert die klassische Erlang/OTP-Invariante:
> - `OneForAll`: *"If any child crashes, ALL children supervised by this supervisor are terminated in reverse registration order and restarted in order of registration."*
> - `RestForOne`: *"If a child crashes, that child and all subsequent children registered AFTER it are terminated in reverse order and restarted in order of registration."*

Während `graceful_shutdown_all()` (`src/actor/supervisor.rs:1257-1282`) diese Invariante exakt einhält (Kind $N$ wird signalisiert, `rx.await` wartet das vollständige Ende von Kind $N$ inkl. `on_stop` ab, und **erst danach** wird Kind $N-1$ signalisiert), werden in `handle_child_failure` und `handle_restart_child` **alle** betroffenen Geschwister in einer synchronen `for`-Schleife **gleichzeitig** terminiert:

```rust
for target_name in children_to_restart.iter().rev() {
    ...
    if is_running {
        let rx = Self::initiate_child_termination(
            self.name.clone(),
            target_name.clone(),
            entry,
        );
        term_receivers.push(rx);
    }
}
```

Das hat zwei schwerwiegende Konsequenzen für abhängige Pipelines (`Stage 1 -> Stage 2 -> Stage 3`):
1. **Ressourcen-/Abhängigkeits-Bruch in `on_stop`:** Wenn `Stage 1` abstürzt, erhalten `Stage 3` und `Stage 2` exakt im selben Moment `shutdown_tx.send(true)` und `ActorEnvelope::Shutdown`. `Stage 2` schließt sofort seine Mailbox (`self.receiver.close()`). Wenn `Stage 3` während seines Mailbox-Drains oder in `on_stop()` noch abschließende Nachrichten an `Stage 2` flushen muss, ist `Stage 2` bereits geschlossen.
2. **Parallele Timeout-Uhren:** Die `ShutdownPolicy::Timeout`-Timer aller Geschwister laufen gleichzeitig ab, anstatt jedem Kind nacheinander sein eigenes Shutdown-Budget zu gewähren.

#### Behebungsanweisung
1. In `handle_child_failure` und `handle_restart_child` sollte zunächst für alle betroffenen Slots synchron `entry.phase = ChildPhase::Restarting`, `entry.restart_ticket = ticket` und `SlotState::Restarting` gesetzt werden (damit Clients sofort blockierungsfrei informiert sind).
2. Die eigentliche Terminierung (`shutdown_tx.send(true)`, `shutdown_signal`, Timeout-Task und das Warten auf `term_rx`) sollte für die laufenden Kinder in `children_to_restart.iter().rev()` im Hintergrund-Task **strikt sequenziell** ausgeführt werden – d. h. Kind $k$ wird erst terminiert, nachdem `term_rx` von Kind $k+1$ auf `true` gewechselt ist.

#### SemVer-Kompatibilität
- **Kein SemVer-Break.**

#### Auswirkung auf `remote`
- **Keine kompilier- oder protokollseitigen Brüche, aber wichtiger Timing-Hinweis für gRPC-Timeouts:**
  - Während eines `OneForAll`- oder `RestForOne`-Restarts wartet ein eingehender gRPC-Aufruf (`ActorNodeService::call` -> `ByteEndpoint::call_bytes` -> `ActorClient::call_timeout` -> `rebind_channel`) auf dem Server darauf, dass der betroffene Slot wieder in `SlotState::Running` wechselt.
  - Durch die streng sequenzielle Terminierung der Geschwister beträgt die maximale Dauer der Stop-Phase bei einer Gruppe aus $k$ laufenden Geschwistern nun $\sum_{i=1}^{k} T_{\text{stop}, i}$ statt $\max_{i} T_{\text{stop}, i}$ (identisch zu `graceful_shutdown_all`).
  - Für schnelle `on_stop`-Hooks (< 1 ms) ist der Unterschied vernachlässigbar. Wenn jedoch mehrere Geschwister unter `OneForAll` langsame `on_stop`-Hooks besitzen, sollte das RPC-Timeout größer gewählt werden als die Summe der `ShutdownPolicy::Timeout`s der gekoppelten Geschwister plus Restart-Backoff.

#### Problembeschreibung
`StatefulActorRunner` besitzt bereits den Mechanismus `CallOutcome::Unprocessed(A::Message)`, um nicht-klonbare `Call`-Nachrichten an `ActorClient::call` zurückzugeben, falls der Actor in `on_start` abbricht (`src/actor/stateful_actor.rs:934-939` und `953-958`).
Wenn der Actor jedoch **während** der Verarbeitung von Nachricht #1 mittels `ctx.fail(...)` (oder wegen eines `handler_timeout` in `execute_call`/`execute_cast`) fehlschlägt, während bereits weitere `ActorEnvelope::Call`-Nachrichten #2 und #3 im `mpsc::Receiver`-Puffer warten, wird `self.receiver` beim `return Err(reason_owned)` gedroppt.

```rust
fn return_unprocessed_calls(&mut self) {
    self.receiver.close();
    while let Ok(env) = self.receiver.try_recv() {
        if let ActorEnvelope::Call { msg, respond_to } = env {
            let _ = respond_to.send(CallOutcome::Unprocessed(msg));
        }
    }
}
```

- **Kein SemVer-Break.**

- **Keine negativen Konsequenzen – erheblicher Gewinn für gRPC-Server-Resilience!**
- In `ByteEndpoint::call_bytes` (`src/remote/endpoint.rs:140-156`) wird das `postcard`-Payload einmal auf dem Server zu `msg: A::Message` deserialisiert und dann an `self.call_timeout(msg, dur)` bzw. `self.call(msg)` übergeben.
- Wenn zwei parallele gRPC-`Call`-Requests (#1 und #2) denselben Actor treffen und Request #1 `ctx.fail(...)` oder ein `handler_timeout` auslöst, während Request #2 bereits in der lokalen Mailbox des Actors eingereiht ist, erhält Request #2 auf dem Server `CallOutcome::Unprocessed(msg)`, bindet innerhalb desselben gRPC-Calls transparent auf Instanz #2 um und liefert dem Remote-Client direkt eine erfolgreiche `OkPayload`-Antwort ohne Netzwerk-Retry und ohne erneute Deserialisierung.

### F-04 [Mittel–Hoch | Korrektheit & Lifecycle]: `SupervisorHandle::shutdown()` und `request_shutdown()` schlagen nach einem Child-Supervisor-Restart stillschweigend fehl

- **Betroffene Stellen:**
  - `src/actor/supervisor.rs:2599-2636` (`SupervisorHandle::request_shutdown`, `SupervisorHandle::shutdown`)

#### Problembeschreibung
Sowohl `request_shutdown` als auch `shutdown` verwenden `self.current_command_sender()`, welches lediglich prüft, ob der **aktuell im Handle gecachte** `Sender` noch offen ist. Wenn `self` ein Handle auf einen **Child-Supervisor** ist und dieser Child-Supervisor zwischenzeitlich abgestürzt und vom Parent-Supervisor als Instanz `#2` neu gestartet wurde, zeigt der im `SupervisorHandle` gecachte `sender` noch auf den geschlossenen Channel von Instanz `#1`. Ein Aufruf von `sub.shutdown().await` sieht über `current_command_sender()` den geschlossenen alten Channel, gibt sofort `Ok(())` zurück und **lässt die laufende Instanz `#2` des Child-Supervisors unberührt weiterlaufen**!

#### Behebungsanweisung
Wenn `current_command_sender()` `None` liefert, sollte über `self.get_sender().await` geprüft werden, ob der Child-Supervisor im Parent in eine neue laufende Instanz übergegangen ist. Falls der Supervisor jedoch bereits `Stopped`, `Failed` oder der Parent ebenfalls beendet ist, **muss** `shutdown()` weiterhin idempotent `Ok(())` zurückgeben:

```rust
pub async fn shutdown(&self) -> Result<(), SupervisorError> {
    let current_tx = match self.current_command_sender() {
        Some(tx) => tx,
        None => match self.get_sender().await {
            Ok(tx) => tx,
            Err(_) => return Ok(()),
        },
    };

    let (tx, rx) = oneshot::channel();
    if current_tx
        .send(SupervisorCommand::Shutdown { respond_to: tx })
        .await
        .is_err()
    {
        return Ok(());
    }

    let _ = rx.await;
    Ok(())
}
```

#### SemVer-Kompatibilität
- **Kein SemVer-Break.**

#### Auswirkung auf `remote`
- **Wichtige Wechselwirkung mit `ActorNodeHandle::shutdown()` (`src/remote/server.rs:870-873`):**
  1. **Positiver Effekt:** Wenn ein Nutzer dem `ActorNodeBuilder::supervisor(service_sup)` einen Child-Supervisor übergibt und dieser Child-Supervisor während der Laufzeit des gRPC-Servers einmal neu gestartet wurde, fährt Phase 2 des gRPC-Node-Shutdowns nun auch die neue Instanz zuverlässig herunter.
  2. **Zwingende Randbedingung für `remote` (Idempotenz):** `Err(_)` aus `self.get_sender().await` innerhalb von `shutdown()` muss auf `return Ok(())` abgebildet werden, damit `ActorNodeHandle::shutdown()` in Zeile 872 nicht mit `Err(RemoteNodeError::Supervisor(...))` fehlschlägt, falls der Supervisor bereits vor dem Node-Shutdown beendet wurde.

### F-05 [Mittel | Korrektheit & Fehler-Reporting]: Verlust des `SupervisorError` (z. B. `MaxRestartsExceeded`) beim letzten Retry-Versuch (`attempt == MAX_ATTEMPTS`)

Wenn ein Aufrufer `remote_client.call_timeout(msg, timeout)` oder `remote_monitor.status(opts)` mit einer Deadline $T$ (z. B. `50ms` oder `DEFAULT_SNAPSHOT_TIMEOUT = 2s`) aufruft, startet der Client **drei Timer mit exakt derselben Dauer $T$**:
1. **Äußerer Client-Timer:** `tokio::time::timeout(timeout, self.call_internal(msg, Some(timeout)))` (`src/remote/client.rs:126`) – startet **vor** der `postcard`-Serialisierung und **vor** dem Senden über den TCP/HTTP2-Socket.
2. **Tonic/HTTP2-Timer:** `request.set_timeout(dur)` (`src/remote/client.rs:153`) setzt den `grpc-timeout`-Header auf $T$.
3. **Server-Handler-Timer:** `timeout_ms: timeout.map(duration_to_wire_ms)` (`src/remote/client.rs:149`) übergibt $T$ im Protobuf-Payload an den Server, der erst **nach** Netzwerk-RTT, Auth-Check, Registry-Lookup und Deserialisierung sein lokales `tokio::time::timeout(T, ...)` startet.

**Negative Folgen:**
1. **Unnötige HTTP/2 `RST_STREAM (CANCEL)`-Abbrüche & unvollständige Server-Metriken:**
   Da der Client-Timer immer um die halbe Netzwerk-RTT + Serialisierungszeit früher abläuft als der Server-Timer, bricht der Client den HTTP/2-Stream per `RST_STREAM` ab, kurz bevor der Server die reguläre Protobuf-Antwort `CallResponse { FrameworkError(Kind::Timeout) }` senden und in `src/remote/server.rs:261` `self.metrics.record_remote_error(err)` zählen kann!
2. **Verlust degradierter `NodeStatus`-Snapshots in `RemoteNodeMonitor::status` (`src/remote/monitor.rs:138-162`):**
   `SupervisorHandle::snapshot_tree_timeout(opts.timeout)` ist auf dem Server explizit so konstruiert, dass ein einzelner hängender Child-Supervisor nach Ablauf von `opts.timeout` **nicht** den gesamten Snapshot scheitern lässt, sondern einen validen `NodeStatus` mit `HealthState::Degraded` und `unavailable_subtrees: 1` zurückliefert!
   Weil `RemoteNodeMonitor::status` (`src/remote/monitor.rs:140, 157, 161`) jedoch auf dem Client dasselbe `opts.timeout` ohne jeden Netzwerk-/Serialisierungs-Puffer als hartes Client-Timeout (`tokio::time::timeout(opts.timeout, ...)` und `request.set_timeout(opts.timeout)`) verwendet, bricht der Client den `Status`-RPC exakt in dem Moment mit `Err(RemoteActorError::Timeout)` ab, in dem der Server den degradierten `NodeStatus` fertiggestellt hat und zurückschicken will!

#### Behebungsanweisung
Trenne in `RemoteNodeMonitor::status` (und analog bei `call_timeout` / `cast_timeout`) das an den Server übermittelte **Ausführungs-Budget** (`timeout_ms`) vom **Transport-Timeout** des Clients bzw. gib in `RemoteNodeMonitor::status` dem Transport-Deadline-Wrapper einen kleinen Netzwerk-/Serialisierungs-Headroom (oder skaliere das Server-Tree-Budget leicht unterhalb des Client-Timeouts):

```rust
// In src/remote/monitor.rs (RemoteNodeMonitor::status_internal):
const STATUS_TRANSPORT_HEADROOM: Duration = Duration::from_millis(100);

async fn status_internal(
    &self,
    opts: StatusOptions,
) -> Result<NodeStatus, RemoteMonitorError> {
    // Dem Server-Tree-Snapshot ein leicht kürzeres Budget geben, damit ein degradierter
    // Baum-Snapshot (unavailable_subtrees > 0) noch vor Ablauf der Client-Deadline
    // serialisiert und über HTTP/2 übertragen werden kann:
    let server_tree_budget = if opts.timeout > STATUS_TRANSPORT_HEADROOM.saturating_mul(2) {
        opts.timeout.saturating_sub(STATUS_TRANSPORT_HEADROOM)
    } else {
        opts.timeout
    };

    let req = self.prepare_request(
        StatusRequest {
            protocol_version: REMOTE_PROTOCOL_VERSION,
            timeout_ms: Some(duration_to_wire_ms(server_tree_budget)),
            include_tree: opts.include_tree,
            include_child_details: opts.include_child_details,
        },
        Some(opts.timeout),
    );
    ...
```

Zudem ist in `call_internal`, `cast_internal`, `health_internal` und `status_internal` das Setzen von `request.set_timeout(dur)` redundant, wenn der Aufruf bereits außen in `tokio::time::timeout(timeout, ...)` gewrappt ist (oder umgekehrt).

#### SemVer-Kompatibilität
- **Kein SemVer-Break.**

### F-18 [Hoch | Performanz & Zero-Copy (`AGENTS.md` §3)]: Vermeidbare Heap-Allokationen im gRPC-Hot-Path (`sanitize_label`, 0-Capacity `BoundedVec`, `String`-Clones pro RPC & `bytes::Bytes`)

- **Betroffene Stellen:**
  - `src/remote/registry.rs:17-31` (`sanitize_label`)
  - `src/remote/server.rs:223-224, 280-281` (`span.record("service", sanitize_label(...))`)
  - `src/remote/endpoint.rs:71-81` (`encode_payload` -> `BoundedVec`)
  - `src/remote/client.rs:146-147, 212-213` (`self.service_name.clone()`, `self.actor_name.clone()`)
  - `build.rs:11` (`tonic_prost_build::configure()`)

#### Problembeschreibung
Gemäß `AGENTS.md` §3 (*Ownership & Zero-Copy*):
> *"Bevorzuge Borrows (`&str`, `&[T]`) gegenüber übermäßigem `.clone()`. Vermeide unnötige Heap-Allokationen bei Netzwerk-Payloads. Nutze `bytes::Bytes` für Puffer und `Arc<T>` für geteilten, unveränderlichen Zustand."*

Im gRPC-Hot-Path finden aktuell bei **jedem einzelnen RPC** mehrere unnötige Heap-Allokationen statt:
1. **2 Heap-Allokationen pro eingehendem RPC durch `sanitize_label` (`src/remote/server.rs:223-224, 280-281`):**
   Am Anfang jedes `ActorNode::call`- und `ActorNode::cast`-Aufrufs führt der Server aus:
   ```rust

   span.record("service", sanitize_label(&req.service_name).as_str());
   span.record("actor", sanitize_label(&req.actor_name).as_str());
   ```
   `sanitize_label` (`src/remote/registry.rs:17-31`) allokiert **immer** einen neuen `String::with_capacity(...)` und kopiert Zeichen für Zeichen – selbst wenn `req.service_name` und `req.actor_name` ganz normale, kurze ASCII-Namen ohne Steuerzeichen sind (99,99 % aller Requests) und selbst wenn der Tracing-Span deaktiviert ist (`span.is_disabled()`)!
2. **Mehrfache Reallokationen in `encode_payload` (`src/remote/endpoint.rs:71-81`):**
   `encode_payload` initialisiert `BoundedVec` mit `buf: Vec::new()` (Kapazität `0`). Da `postcard` Felder inkrementell per `try_push` (1 Byte) und `try_extend` schreibt und `BoundedVec::try_extend` exakt `self.buf.reserve(next_len - self.buf.len())` reserviert, durchläuft der `Vec` bei jeder Serialisierung mehrere kleine Reallokationen (`0 -> 4 -> 8 -> 16 -> 32 -> 64 Bytes`).
3. **`Vec<u8>` statt Zero-Copy `bytes::Bytes` bei Prost (`build.rs:11`):**
   Weil `tonic_prost_build::configure()` ohne `.bytes(["."])` aufgerufen wird, generiert Prost `Vec<u8>` für alle `bytes`-Felder in `actor_node.proto`. Dadurch muss Prost beim Decodieren jedes HTTP/2-Frames aus dem `hyper`/`h2`-`Bytes`-Buffer ein neues `Vec<u8>` auf dem Heap allokieren und kopieren, statt einen Zero-Copy-`Bytes`-Slice zu übergeben.

1. **Zero-Allocation Fast-Path für `sanitize_label` mittels `Cow<'_, str>` (`src/remote/registry.rs:17-31`) – SemVer-kompatibel:**

## 4. Zusammenfassung der Auswirkungsanalyse & Release-Roadmap (`v0.3.4` vs. `v0.4.0`)

### Drei zentrale Leitplanken für das Zusammenspiel von `actor` und `remote`
1. **Leitplanke 1 (zu F-06 – `Instant`-Kompatibilität):** `SupervisorHandle::started_at(&self) -> std::time::Instant` und `LocalNodeMonitor::with_started_at(self, started_at: std::time::Instant)` **müssen** beim Typ `std::time::Instant` bleiben, da `ActorNodeAdminService::status` (`src/remote/server.rs:492`), `examples/remote/monitor.rs:61` und `tests/remote_grpc_test.rs:792, 901` direkt `std::time::Instant` übergeben.
2. **Leitplanke 2 (zu F-04 – Idempotenz von `SupervisorHandle::shutdown`):** Wenn `SupervisorHandle::shutdown()` über `get_sender().await` ein Rebinding versucht und feststellt, dass der Supervisor bereits gestoppt oder beendet ist (`Err(_)`), muss `shutdown()` zwingend `Ok(())` zurückgeben, damit Phase 2 in `ActorNodeHandle::shutdown()` (`src/remote/server.rs:872`) idempotent bleibt.
3. **Leitplanke 3 (zu F-13 – Tracing-Spans):** `ActorContext`-Hintergrundtasks (`send_interval`, `spawn_scoped`, `forward_receiver`) müssen an den Span der Actor-Task-Instanz gebunden werden, nicht an kurzlebige Tonic-`grpc_call`-Request-Spans.
